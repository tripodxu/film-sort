## 2. 发现清单（本轮全部修复）

严重度口径：**P1** = 承诺的能力悄悄失效 / 新功能在真实数据上算错；
**P2** = 特定路径下用户可见的错误或资源无界；**P3** = 可维护性与防漂移。

### F-01 · P1 · Worker API 日志脱离 `waitUntil` 生命周期

- **位置**：`worker/index.ts:385-433`（`logQueue` / `enqueueLog` / `flushLogs` / `logApiCall`），
  调用点 `:2906`、`:2936`。
- **证据**：`ctx.waitUntil(logApiCall(...))` 里 `logApiCall` 只做一次同步 `enqueueLog` 就 resolve；
  真正的 D1 批量写发生在 `enqueueLog` 用裸 `setTimeout(..., 5000)` 排的回调中
  （`:400` 的 `void flushLogs()` 同理，也没有 `await` / `waitUntil`）。
- **影响**：`waitUntil` 在入队瞬间就认定「后台任务完成」，响应返回后 isolate 可被回收。
  本站是低流量个人站，两个请求间隔常大于 5 秒 → **低流量时日志最容易整批丢**，
  而 `api_logs` 恰恰是用来排查低流量时段异常的那张表。故障表现是「后台统计里查不到记录」，零报错。
- **附带**：日志状态（队列 / 调度标志 / cachedDB）是 2980 行入口里的模块级全局变量，
  没有可注入的时钟与 DB，无法独立测试——这是缺陷长期没被发现的原因。
- **修法**：抽 `worker/apiLog.ts`，把 flush 的 promise 交给 `ctx.waitUntil`；补可注入时钟的单元测试。
  见计划 **O-01**。

### F-02 · P1 · AI 上游竞速兜底定时器从不清理

- **位置**：`worker/ai.ts:615-629`。
- **证据**：`Promise.race` 的第二分支
  `new Promise<never>((_, reject) => setTimeout(() => reject(new Error("fetch race timeout")), timeoutMs + 5000))`
  没有保存 timer、没有 `clearTimeout`。对照 `worker/deadline.ts:27-39` 的 `withDeadline`
  已经用 `finally { clearTimeout(timer) }`——同一仓库里两种写法，前者是漏的。
- **影响**：每次 AI 点评 / 模型探测，即使 200 ms 就成功返回，也会残留一个最长 **65 秒**的定时器。
  在 workerd 里这会推迟 isolate 回收、放大并发期内存；AI 通道被批量调用时线性累积。
- **修法**：保存 timer 并在 `finally` 清理，补「快路径不留 timer」测试。见 **O-02**。

### F-03 · P1 · 新增「精华切片」：脏数值击穿 + 恒等三元 + novelty 语义漂移

- **位置**：`src/lib/essenceSlice.ts:76-91`、`:140-148`；调用方 `src/components/GalleryBento.tsx:146-152`。
- **证据与三个子问题**：
  1. `prepareCandidate` 用 `typeof candidate.year === "number"` 放行，但 `NaN` / `Infinity` 也是 number。
     `Math.abs(NaN - 2000)` → `NaN` → `1 - NaN/30` → `NaN` → `Math.max(0, NaN)` → `NaN`，
     `preparedSimilarity` 返回 `NaN`，`novelty` 整列变 `NaN`，`novelty[i] > novelty[best]` 恒 false，
     **最远点采样退化为「按顺序取前 N 件」**，正是该功能宣称要避免的结果。
     用户导入的 TXT/JSON 清单完全可能带 `year: null` / 非数字字符串 / 越界值。
     同理 `creatorKey` 的 `creator?.trim()` 在运行时拿到非字符串会抛 `TypeError`，直接把 gallery 画像页打进 ErrorBoundary。
  2. `picks` 里 `return { index, novelty: order === 0 ? nearest : nearest }` —— **三元两分支完全相同**，
     `order` 参数成了摆设（类似 PITFALLS 4.39 记录的「恒真断言」）。
  3. 采样过程中维护的 `novelty[]`（该件被选中时相对**当时**已选集合的最小距离）在选中后被写成 `-1` 丢弃，
     `picks` 又用「与**最终全部**切片的最小距离」重算了一遍。接口文档 `EssencePick.novelty` 写的是
     「该件与已选集合的最小相似度」——与实际值不是同一个量。
- **修法**：`finiteYear` / `safeText` 守卫；采样时保存 novelty；删掉恒等三元；补脏数据 / 语义不变量测试。见 **O-03**。

### F-04 · P2 · 精华切片 `<li key={work.id}>` 在缺 id 清单上重复 key

- **位置**：`src/components/GalleryBento.tsx:303-308`。
- **证据**：`Artwork.id` 是可选字段（`src/data/media.ts`），手动录入与文本导入的作品普遍没有 id；
  一次渲染里多个 `key={undefined}` 触发 React 重复 key，DOM 被错位复用，
  而「代表 N 件」来自 `essence.represented[order]`（按位置取），**文案会贴到错误的作品上**。
  同类事故已在 `PITFALLS.md` 4.66（翻译标签撞车）记录过，这次是「缺失 id 撞车」。
- **修法**：用 `work.id ?? 稳定下标键`，补源码绊线 / 纯函数断言。见 **O-03**（同批次）。

### F-05 · P2 · Service Worker 缓存无 hash 的固定 URL

- **位置**：`public/sw.js:69-82`（静态资源 cache-first 分支）；`worker/index.ts:2857-2865`。
- **证据**：cache-first 只判 `status === 200 && response.type === "basic"`，**不看 `cache-control`**。
  而 `/admin/app.js` 由 Worker 动态生成且明确 `cache-control: no-store`，
  `/vendor/chart.umd.js` 是不带 hash 的固定路径。两者都会被 `cache.put` 写进 `RUNTIME_CACHE`。
  桶名是 `art-rank-v4-<BUILD_ID>`，`BUILD_ID` 只在前端构建时变——
  **只改 Worker 脚本、不动前端构建时 BUILD_ID 不变，旧桶不会被清，后台永远跑旧 JS**。
  这正好是 `PITFALLS.md` 1.7「SW 缓存导致部署不生效」的另一种形状。
- **修法**：把无 hash 的管理后台资源列入 network-first 名单（离线仍回退缓存），
  并跳过带 `no-store` 的响应不写缓存；补 `pwa.test.ts` 断言。见 **O-04**。

### F-06 · P2 · 动态榜单列表用数组下标作 React key

- **位置**：`src/views/CompareView.tsx:286`、`:320`；`src/App.tsx:1898`。
- **证据**：三处都是 `peer.rankings` / `profile.rankings` 的 `.map((entry, idx) => ... key={idx})`，
  列表来自用户导入、可增删可换序。下标 key 会让 React 在换 profile / 删榜单时复用上一份的 DOM，
  勾选状态、展开态、焦点位置可能串到另一行。
- **修法**：改用内容稳定键 `kind|collectionTitle`（必要时带下标兜底去重），补源码绊线。见 **O-05**。

### F-07 · P2 · 两处事件处理器定时器在卸载后仍 setState

- **位置**：`src/views/ProfileView.tsx:134`（`setPublishBurst(false)`）、
  `src/views/ShareView.tsx:170`（`setCopied(false)`）。
- **证据**：都是事件处理器里裸 `setTimeout`，没有 ref 保存、没有 effect 清理。
  同仓 `AiInsightCard.tsx:55-62`、`useAuth.ts:408-417`、`App.tsx:585-589` 都已按「ref + 卸载清理」写好，
  这两处是 `4bc3572` 定时器批的漏网。
  `ShareView` 还有第二个可观察症状：**连点两次复制**，第一次的 2 秒定时器会提前把「已复制」复位。
- **修法**：统一到 ref + 卸载清理 + 重设前先清旧定时器；把 `src/lifecycle.test.ts` 从只查
  `setInterval/clearInterval` 扩到覆盖这两处。见 **O-06**。

### F-08 · P2 · 海报失败上报去重集合无上界

- **位置**：`src/components/Poster.tsx:181`、`:324-334`。
- **证据**：`const reportedFailures = new Set<string>()`，键是 `${kind}|${work.title}|${url}`（含完整 URL），
  只有 `add`、没有淘汰。长会话里反复浏览广场/大清单，失败图越多集合越大，且强引用 URL 字符串不释放。
- **修法**：加上界（超限清半），保留「同一 URL 不重复上报」语义；补纯函数测试。见 **O-07**。

### F-09 · P3 · 两份 localStorage 配置存取逐行重复

- **位置**：`src/lib/aiInsight.ts:61-103`（`readAiConfig/writeAiConfig/clearAiConfig`）与
  `src/lib/typesafe.ts:27-54`（`readTypesafeConfig/writeTypesafeConfig/clearTypesafeConfig`）。

- **修法**：抽 `src/lib/localConfig.ts` 的 `readJsonConfig/writeJsonConfig/clearConfig`，
