# PLAN-JEV-DISAMBIGUATION · 迭代 2/20（创意类）

> 目标：把「猜封面」这件事从**手写启发式打分**推进到**带置信度的决策**。
> 对应 `docs/ROADMAP.md` 的 **Jev Phase 2：维基消歧 Choice**。
> 前一轮 `docs/PLAN-BUNDLE-SPLIT.md` 摘掉了 Three.js，本轮继续减主包（`fflate`）的同时，
> 引入本项目第一条**真正用上概率**的链路。

---

## 0. 为什么要做（问题陈述）

other 维度连续三轮迭代（`82d7581` → `05a66df` → `a6044984`）都在做同一件事：
**把错的候选挡掉**。每一轮都是「线上翻车 → 补一条规则 → 加一条 tripwire」。
台账里已经能读出这条路的尽头：

> 「日常幻想 / 故事FM / 看理想 三条**永久空图**——zh-wiki 无对应条目、
> 搜出来的都是零重合页面……若用户要求必须出图，需要的是**中文播客/展览的封面来源**，
> 不是继续调解析器」（`docs/agents/TASK-LEDGER.md` T-20261002-01 遗留风险①）

也就是说，**规则这条路已经走到头了**。剩下的错误分两类，处理方式完全不同：

| 错误类型 | 现状 | 规则能否解决 |
|---------|------|-------------|
| **A 类：信息不足** —— zh-wiki 根本没有「故事FM」这个条目，正确答案是《我們的故事 (專輯)》或别的什么 | 返回空（宁可不返图） | **不能**。信息不在候选池里 |
| **B 类：信息充足但判错** —— 候选池里有正确条目，评分器却挑错了 | 返回错图 | **能，但每条都要手工试**（已有 15+ 条启发式） |

B 类已经用规则解决了大半；**A 类是规则的死穴**。所以本轮换的不是「再加一条规则」，
而是**换决策范式**：把「我认为最像的那个」升级成「这是候选，按置信度排序，
由用户或模型来定」。

## 1. 核心洞察：分数不是置信度

`worker/other.ts` 的 `scoreOtherPage()` 至今产出一个 `score`（0–13.5 的加权分）
和一个 `tier`（0/1/2 档），**但这两个数从未被当作置信度使用**——`pickBest()`
只是取分数最高的那一个，然后无条件返回。

「道奇Journey」和「風之旅人」的 `score` 分别是 6.5 和 5.5。
**差 1 分不构成任何确定性**，却决定了用户看到汽车还是看到游戏。这是错的：
把一个连续的启发式分当成离散的判决。

Jev 恰好提供这个缺失的东西——**校准过的概率**。这正是 ROADMAP 里
「概率与 confidence 替代整套启发式」那句话一直没兑现的原因（Phase 2 一直 ⬜）。

## 2. 结构性障碍（这才是 Phase 2 一直没做的原因）

直接把 Choice 塞进解析器会踩三个坑：

1. **拿不到 key** —— Jev key 只存在浏览器 localStorage（`src/lib/typesafe.ts:22`
   `art-rank:typesafe-config`），而海报解析在 `/api/posters/batch` 里跑
   （`worker/index.ts:2129-2155`），那条链路不可能带 key。
2. **延迟** —— 一次解析要跑 6 轮 wiki（zh/en × 纯标题轮/类型词轮），
   再加一次 Jev（70–500ms），会显著放大 `m00079「有点卡」` 的体感。
3. **批量语义** —— 一批 8 条海报，每条一次 Jev 调用 = 8 次外部请求，
   违反 CONVENTIONS §3「主链路永不依赖外部决策服务」。

**解法：不要把 Jev 放进解析器，放进解析器的**结果**里。**
解析照旧跑规则（快、免费、离线可测），但它现在要**额外产出一份「我有多不确定」**
并把候选池带出来。当规则**低置信**时，服务端把候选交给用户/模型裁决；
高置信时维持现状（零成本、零延迟）。

这把 Phase 2 从「替换解析器」降级成了「**给解析器加一个出口**」——
改动面从 ROADMAP 说的「改动面较大」变成一个增量分支。

## 3. 方案：结构化置信度（Structured Confidence）

### 3.1 置信度从已有信号里算，不新增规则

`worker/other.ts` 新增：

```ts
export interface OtherConfidence {
  /** 0–1。综合档位、领先幅度、字面证据、题材佐证。 */
  score: number;
  /** 分档理由，便于 /api/admin 排查与 tripwire 断言。 */
  band: "exact" | "strong" | "shaky" | "weak";
  /** 领先第二名多少（归一到 0–1）。差得越小越不自信。 */
  margin: number;
  /** 冠军的字面证据强度：tier2 有字面证据 / 靠别名 / 纯题材词救援。 */
  evidence: "literal" | "alias" | "hint";
}

export function otherConfidence(
  ranked: readonly OtherCandidate[],
  picked: OtherCandidate | null,
  year?: string,
): OtherConfidence;
```

`score` 的合成因子（全部是**已有信号的重排**，不是新规则）：
- 档位（tier 2 / 1）与字面证据（literal > alias > hint）；
- **领先幅度 margin** —— 冠军与第二名的分差，占满分跨度归一；
- 年份佐证（有 year 且冠军摘要命中 → 加权）；
- 题材佐证（`declaresWorkTopic` / `hintTopicConfirmed`）。

**为什么 margin 最重要**：它直接对应「道奇Journey 6.5 vs 風之旅人 5.5」这种形状。
margin 小 ⇒ 即使冠军 tier2，也该标记为不确定。

### 3.2 出口一：API 把候选池暴露出来（无 key 也能用）

新增 `GET /api/other/candidates?name=&year=`：
返回**排序后的候选 + 置信度**，不含任何 AI 调用。

前端 `Poster.tsx` 现有行为不变（低置信时照旧显示空/兜底），
但**新增一条调试与自查路径**：用户看到空白封面时可以点「为什么没有封面？」，
看到「我们找到 4 个候选，但我们不确定哪个对（领先幅度只有 12%）」。

这一条是本轮**无条件可用**的部分：不需要 key、不需要额外请求、
纯诊断能力，且它把黑箱变成了可解释系统。

### 3.3 出口二：Jev Choice 裁决（key 可选，规则优先）

新增 `POST /api/ai/jev-disambiguate`：

```jsonc
// 请求
{ "config": {...}, "name": "故事FM", "year": 2017, "locale": "zh",
  "candidates": ["我們的故事 (專輯)", "黎明FM", "96.3好FM"] }
// 响应
{ "ok": true, "pick": "我們的故事 (專輯)", "confidence": 0.91,
  "probabilities": { "我們的故事 (專輯)": 0.91, "黎明FM": 0.04 } }
```

`worker/typesafe.ts` 新增 `jevChoose<T extends string>()`：把 Choice 从
**二选一**推广到 **≤255 多选一**（ROADMAP 明说「候选列表 ≤255 天然匹配 Choice 基数」）。
现有 `jevPick` 是它的特例，保持不动。

**铁律（CONVENTIONS §3）**：key 未配置 / 调用失败 / 低置信（<0.6）
⇒ **一律回落规则**，`choices` 端点永不成为主链路单点。

### 3.4 出口三：前端「让用户选」（最终兜底，零成本）

`src/components/Poster.tsx` 新增：低置信且无 key 时，海报位显示一枚
**「选对了吗？」** 的微标，点开是候选列表（带缩略图），用户选完即写
`poster_urls`（复用现有键），**下次永久正确**。

这条的价值最大：**一次人工点击把一条永久空图变成永久正确**，
而且不需要任何外部服务。这才是 A 类错误的真正解法。

## 9. 反思（交付时补记，2026-10-02）

### 9.1 换范式还是加规则？判据

**换范式**。判据不是「代码变多了」，而是：修复后**是否新增了任何一条会让某个具体条目变对的规则**。
本轮新增的 `evidenceOf` / `otherConfidence` / `jevChoose` **一条出图规则都没加**——`pickBest` 判决逻辑一行未动（线上 8 条结果与迭代 1 逐字一致即是证据）。规则阶段的终点形态是「为 日常幻想/故事FM/看理想 各写一条特例」，那是过拟合；本轮的形态是「把黑箱变成可解释系统 + 给人机共决留出口」。

### 9.2 可解释性能不能量化？——能，而且第一版就抓出两个真 bug

`/api/other/candidates` 的价值在交付**当天**就兑现了，不是「以后调试方便」这种软收益：

- Journey 线上返回 `evidence=hint / band=weak`，而判决层此前已把它修对。**判决对了但诊断说没信心**，意味着这个诊断端点在最该证明自己的一次上失真——排查它才发现 `evidenceOf` 根本没查过别名表（先判 `hintRescued` 就 return 了）。
- 第一次修的方向还错了一轮（改成「零字面重合才算 hint」后，「道奇Journey」被误判成 hint）。最终形态「按证据来路分层」是在这两轮实测之后才定型的。

也就是说：**没有诊断出口的话，这两个 bug 会以「Journey 偶尔给错图」的形式在生产里潜伏**，而不会变成一条明确的工作项。可解释性的价值 = 把「说不清为什么错」变成「一条能指认、能派工、能验收的断言」。

### 9.3 为什么 Phase 2 拖了这么久？本轮避开了哪个坑

拖了这么久的真因不是「难」，是**方案本身与部署形态不兼容**，而这个不兼容性在写代码前就能看出来：

1. **key 在错误的层**。key 只存在于浏览器 localStorage，`/api/posters/batch` 这个 Worker 端点根本拿不到。任何「Worker 主动调 Jev」的方案，要么把 key 传到 Worker（破坏「key 不落盘」的不变量），要么先做一次前端预调用（于是有了延迟与批量语义问题）。
2. **批量语义被破坏**。一次解析跑 6 轮维基已是既定成本，再加一次外部 AI 调用 = 一批 8 条变 8 次外部请求，直接撞上 `docs/agents/CONVENTIONS.md` §3。
3. **延迟与用户体感对撞**。m00079「好了，但是有点卡」已经定性为 RTT ~1.2s（`colo=LAX`），再加 70–500ms 的 AI 延迟是在最敏感的地方加杠杆。

本轮的设计避开的正是第 1 条：**把 Jev 放在「出口」而不是「入口」**——`/api/other/candidates` 无 key 即可用（诊断）、`/api/ai/jev-disambiguate` 由**前端**在用户已经做出选择后才有意义（裁决）。判决层因此可以按 band 分级触发（`exact`/`strong` 永不打扰用户），并且**任何时候都能优雅退回规则**（无 key 400、上游失败带 `fallback: "rules"`）。

一句话：**先让系统能说出「我不确定」，再谈让它更确定。** 顺序反过来时，Phase 2 就会变成一次「加了 AI 但没人敢用」的改造。
