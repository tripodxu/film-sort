## 0. 执行纪律（每一步都不可省）

### 每点的固定四步

| 步 | 动作 | 判据 |
|----|------|------|
| ① 优化 | 只改该点涉及的文件，不夹带无关重构 | `git diff --stat` 的文件清单与计划一致 |
| ② 审核 | 读 `git diff` 全文；核对「有没有改到不该改的」「有没有把断言喂绿」「有没有漏调用点」 | 逐调用点 grep 确认；新增测试必须能「把故障改回去就变红」 |
| ③ 验证 | `npm run check` → `lint` → `format:check` → `test -- --run` → `build`，五道全绿；收尾批次额外跑 `npm run gates`（含 `docs:facts` + `dev:smoke`） | 逐道看 **exit code**，不看管道里的 `OK` 字样（`gates.mjs` 的立身之本） |
| ④ 提交 | `git add <本点文件>` → `git -c commit.gpgsign=false commit --no-gpg-sign -m "..."` | Conventional Commits 中文描述；一次一点；不 `push` |

### 本轮硬约束

- **不签名**：仓库级 `commit.gpgsign=true`，每次提交显式 `--no-gpg-sign`。
- **不使用子代理**：全部读写、验证、提交由主会话完成。
- **不推送、不部署**：本轮只到 commit；线上验证按铁律留给 push 之后，所有状态标「待线上复核」。
- **零视觉改动**：10 个点都不碰颜色 / 布局 / 尺寸 / 字体；因此不需要跑 `ui-shot` 像素基线
  （`AGENTS.md` §5 的截图要求针对视觉改动）。
- **绊线纪律**：新增断言一律先剥注释再扫（`PITFALLS.md` 4.48），并做一次「把修复倒回去断言应变红」的红队自检。
- **文档不写硬编码计数**（`MEMORY.md` 约定）：测试数、迁移数、缓存版本一律以命令输出为准。

## O-01 · Worker API 日志纳入 `waitUntil` 生命周期 · ⬜

- **对应**：F-01（P1）、F-10（P3）。
- **改动范围**：新增 `worker/apiLog.ts`、`worker/apiLog.test.ts`；改 `worker/index.ts:385-433` 与两处 `ctx.waitUntil` 调用点。
- **改法**：
  1. 把 `logQueue` / `flushLogs` / `logApiCall` 收进 `ApiLogQueue` 类（可注入 `D1Database` 与调度函数），
     `index.ts` 保留一个模块级实例，对外 API 形状不变。
  2. `enqueue(ctx, entry)`：达阈值时立即 `flush()`，否则排一次延迟 flush；**两种情况产生的 promise
     都注册 `ctx.waitUntil`**，并把当前挂起的 flush promise 复用给后续请求，避免多请求各排一个定时器。
  3. `flush()` 仍然「日志失败绝不阻断请求」，但失败不再被无声吞掉计时生命周期。
- **验收测试**（`worker/apiLog.test.ts`）：
  - 快路径：入队 → 推进时钟 → fake DB 的 `batch` 收到正确行数，且 `ctx.waitUntil` 收到的 promise 在该写入**之后**才 resolve（行为断言，不是调用次数断言）。
  - 达阈值：第 50 条触发立即 flush，且不额外排 5 秒定时器。
  - `flush` 抛错时不 reject、不影响主请求。
- **风险与回退**：日志写 D1 的 SQL / 批次大小一字不改，只改「谁等它」。回退 = 还原 `index.ts` 这一段 + 删新文件。
- **提交**：`fix(worker): API 日志 flush 纳入 waitUntil 生命周期并抽出可测模块`。
