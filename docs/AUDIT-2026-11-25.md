## 3. 已确认并修复的问题

### N-01 · P1（回归）· 主题「示例模板」必然导入失败

- **引入提交**：`acd7d8b`（台账记为 T3–T4「统一自定义主题模板 / 变量提示」）。
- **原位置**：`src/components/ThemeImportDialog.tsx` 的 `THEME_TEMPLATE`。
- **根因**（两层，各自都足以让导入失败）：
  1. 元数据写的是 `"dot":"#d8f86a"`（字符串），而 `themeRegistry.parseMeta` 要求 `dot` 是**长度为 2 的数组** → `meta_invalid`；
  2. 即便修好 `dot`，模板还缺 21 个必需变量中的 9 个（`--text-2 --text-3 --muted --line --border-2 --surface --surface-2 --surface-3 --surface-hover`）→ `var_required_missing`。
- **实测**：把修复前的模板原文喂给 `parseThemePackage`，返回 `{"ok":false,"error":"meta_invalid"}`。
- **影响**：「填入示例模板」和「复制模板」两个新按钮产出的内容无法导入；用户照着模板改颜色，得到的只会是一条与自己的修改无关的报错。未知变量又会被 `var_unknown` 拒绝，用户没有自学成功的路径。
- **修复**：
  - 模板移到 `src/lib/themeTemplate.ts`，写成一份合法主题包（`dot` 为数组、21 个必需变量齐全、另带 11 个常用变量），块外注明「改 id 要同步改声明块」；
  - 新增 `themeTemplate.test.ts`，用**真实解析器**断言模板可导入、只改 id 仍可导入、删必需变量时给出缺失清单。
- **测试**：4 项。

### N-02 · P1（回归）· 分享链接与比较链接共用同一个输出区

- **引入提交**：`acd7d8b`（台账记为 F5「分享链接生成失败提示与弹窗复用补齐」）。
- **原位置**：`src/App.tsx` 的 `generateShareLink` 与 `share`；`src/views/ProfileView.tsx` 的分享输出区。
- **根因**：`share()`（按钮「复制比较链接」）把 `compareUrl` 写入 `shareUrl` 并生成 `qrUrl`；`acd7d8b` 让 `generateShareLink`（按钮「复制分享链接」）也执行 `setShareUrl(data.url)`，但输出区的输入框写死了 `aria-label="比较链接"`、二维码写死了 `alt="比较二维码"`，且没有清掉或更新 `qrUrl`。
- **影响**：
  - 点「复制分享链接」后，下方输入框被标注为「比较链接」，内容却是分享链接（带有效期的只读页面，对方进去不是 PK 界面）；
  - 如果之前生成过比较链接，旁边的二维码仍然指向那条比较链接——**文本与二维码指向两个不同的页面**；
  - 读屏用户听到的名称与实际内容不符。
- **修复**：
  - 新增 `shareLinkKind: "compare" | "share"` 状态，随链接类型切换；输出区的输入框名称与二维码描述统一由 `shareOutputLabels(kind, t)` 给出；
  - 分享链接也生成自己的二维码（两者都走同一个 `makeQr`），二维码失败时留空，文本框仍可复制；
  - 两类请求共用 `shareGenRef` 代际守卫：「复制比较链接」没有 `disabled={busy}`，两类请求可以并发，先发但迟到的响应一律丢弃，不覆盖用户最后一次选择；
  - 持久化画像时一并重置类型。
- **测试**：3 项（标签行为 + 输出区接线 + 两处写入都必须「先声明类型、再写链接、再换二维码」）。

### N-03 · P2 · 平台连接状态查询：「查不到」被当成「未连接」，且登出后残留上一账号信息

- **原位置**：`src/lib/usePlatformConnect.ts` 的 `checkStatus` 与状态 effect。
- **原逻辑**：`fetch` 无超时、不看 `response.ok`、无代际守卫；`catch { setConnected(false) }`；effect 开头 `if (!active || !accountToken) return;`。
- **影响**：
  - 一次网络抖动、一次 502 或一次 JSON 解析失败，就会把已连接的平台显示成「未连接」——用户可能因此重新扫码或重复提交 Cookie；
  - 登出后 `connected` 与 `accountInfo`（上一账号的昵称、头像）不被清理，切换平台时旧平台的连接态会一直显示到新请求返回；
  - 断开连接期间若有在途的状态响应，旧快照可以把 `connected` 写回 `true`。
- **修复**：
  - 抽出 `requestPlatformStatus(platform, token, fetchImpl)`：10 秒超时，只认 2xx 且 `connected` 为布尔值的响应；其余一律返回 `ok:false`；
  - Hook 中 `ok:false` **保持原状态不动**；每次请求递增 `statusGenRef`，迟到响应丢弃；
  - 登出（token 清空）与「平台 / 账号」范围变化时先清空连接态与昵称头像，并让在途响应失效；
  - 断开成功后递增代际，旧快照无法复活。
- **测试**：11 项行为测试（2xx 采纳、401/403/429/500/503、畸形 JSON、字段缺失、非布尔、网络错误）+ 1 项接线绊线 + 1 项断开绊线。
- **说明**：上一轮报告建议的是 15 秒，本轮取 10 秒——状态查询是只读轻请求，与轮询（15 秒）、发码（20 秒）区分开，黑洞网络下最多等 10 秒。

### N-04 · P2 · 扫码确认后 900 毫秒自动关闭弹窗实际从不生效

- **原位置**：同 Hook 的轮询 `confirmed` 分支。
- **根因**：回调写的是 `if (!stopped) setQrOpen(false)`，而 `setQrState("confirmed")` 改变了轮询 effect 的依赖 → React 先执行旧 effect 的 cleanup，把 `stopped` 置为 `true` → 900 毫秒后 `!stopped` 恒为 false。**这个自动关闭从写下那天起就没有执行过**（上一轮修复前后都一样）。
- **影响**：扫码成功后弹窗停在「已确认」，用户必须手动关闭；提示文案承诺的「成功后自动关闭」没有发生。
- **修复**：改用发码代际 `issueGenRef` 守卫——关闭弹窗与重新发码都会递增代际，迟到的自动关闭被丢弃，因此不会误关用户刚重新打开的弹窗（符合硬规则 7）。
- **测试**：1 项绊线（禁止再依赖 `stopped`，并要求代际守卫存在）。

### N-05 · P2 · Cookie 提交没有超时，可把按钮永久锁死

- **原位置**：同 Hook 的 `connectWithCookie`。
- **原逻辑**：唯一一个没有 `AbortSignal.timeout` 的请求。
- **影响**：黑洞网络（连接挂起不拒绝）下 `cookieBusy` 永久为 `true`，提交按钮一直禁用且无法取消，只能刷新页面。
- **修复**：增加 20 秒超时；`finally` 中的 `setCookieBusy(false)` 保证一定复位。
- **测试**：1 项绊线。

### N-06 · P3（回归）· 新搜索无结果时，旧候选继续显示

- **引入提交**：`8e65a76`（F2「搜索 8 秒超时守卫与直接按名称添加兜底」）。

## 5. 未修问题与后续建议

### R-01 · P3 · 发码接口非 2xx 被当成「二维码过期」并触发自动换码

- `issueQr()` 对 401 / 429 / 5xx 同样执行 `response.json()`，因缺少 `unikey / code` 而抛错 → `setQrState("expired")` → 进入上一轮新增的自动换码分支，最多再打两次限流端点，最后显示「刷新次数已达上限」而不是真实原因（登录失效或被限流）。
- 本轮没有改：需要给 `expired` 增加来源区分并调整自动换码的触发条件，属于状态机形状变更，应单独一个提交并补终态矩阵测试。
- **建议**：非 2xx 时进入独立终态并显示服务端 `error`，不自动重试。

### R-02 · P3（可访问性）· 对决页「略过 / 暂放」点击后强制失焦

- `275cbf2` 在两个按钮的 `onClick` 里加了 `event.currentTarget.blur()`。目的（避免下一对渲染时焦点落在已消失的按钮上）合理，但键盘用户用 Enter 触发同一次 `click`，结果是**每次操作后焦点掉回 `body`**，需要从头 Tab 才能继续。
- **建议**：失焦后把焦点显式移到稳定容器（如对决区的焦点锚点），而不是 `blur()` 了事。

### R-03 · 流程 · 台账自相矛盾，且「已走查」的批次带回归上线

- `docs/agents/TASK-LEDGER.md` 的 `T-20261124-FRONTEND-34` 状态为「✅ 完成（线上实机走查通过）」，同一条目的「验证状态」却仍写「待运行全量 `npm run gates`、推送至 `main` 并 `npm run deploy`」。两句话不可能同时为真。
- 同一批次引入的 N-01、N-02 都是**单击即可复现**的回归。这说明当时的走查没有覆盖「新按钮的产物能否走通下一步」。
- 我没有改动该条目——无法确认哪一句是事实，应由负责人回填。
- **建议**：给台账加一条硬约束——标 ✅ 前，验证状态一栏必须写成过去时并列出证据（资产哈希 / 冒烟结果），不保留「待…」句式。

### R-04 · P3 · 「复制比较链接」按钮没有 `disabled={busy}`

- 两类链接请求可以并发。本轮用代际守卫保证了「最后一次选择胜出」，但 `busy` 会被先完成的那个请求解除，按钮在后一个请求仍在进行时就可再次点击。
- **建议**：给两个按钮统一加 `disabled={busy}`，或把 `busy` 改为计数。

## 8. 部署后的最小验收清单

1. **主题模板**：设置 → 导入主题 →「填入示例模板」→ 直接导入，应成功并出现在主题列表；只改 `id` 与 `[data-theme="…"]` 后再导入也应成功。
2. **分享链接**：画像页先点「复制比较链接」再点「复制分享链接」，下方输入框名称应为「分享链接」、二维码描述为「分享二维码」，且二维码扫码后是分享页而不是 PK 页。
3. **状态查询容错**：已连接状态下把 `/api/netease/status` 拦截为 503 再进入来源页，应保持「已连接」而不是变成「未连接」。
4. **登出清理**：登录并连接豆瓣后登出，重新打开来源页，不得残留上一账号的昵称与头像。
5. **扫码自动关闭**：完成一次真实扫码确认，弹窗应在约 1 秒后自动关闭；确认前手动关闭弹窗，不得被迟到的自动关闭影响下一次打开。
6. **Cookie 提交超时**：把 `/api/douban/cookie` 请求挂起，20 秒后提交按钮应恢复可用。
7. **主链路回归**：真实账号分别完成一次网易云、豆瓣连接与清单导入（上一轮清单第 6 条，仍未做）。
