# HANDOFF — 多 Agent 接力协议

> 目标：**让下一个 agent 在看不到上一段对话的前提下，5 分钟内接上工作。**
> 铁律：**交接内容必须落在仓库文件里**（台账 / commit message / PR 描述），对话内容对下一个 agent 不可见。

---

## 1. 交接四件套（每次交接必须齐备）

| # | 内容 | 写在哪 |
|---|------|--------|
| 1 | **改了什么** | `docs/agents/TASK-LEDGER.md` 条目 + commit message |
| 2 | **为什么这么改** | 台账条目的「决策」；非显然的理由追加到 `docs/memory/DECISIONS.md` 顶部 |
| 3 | **验证到哪一步** | 台账条目的「验证状态」：单测 / 本地 / **线上**（三者要区分） |
| 4 | **下一步是什么** | 台账条目的「下一步（给接手者）」，要具体到文件名与函数名 |

缺任何一件，视为**未完成的交接**，接手者有权先补齐再继续。

---

## 2. 台账条目格式（复制到 `docs/agents/TASK-LEDGER.md` 顶部）

```markdown
### T-YYYYMMDD-NN · <任务标题>
- **状态**：🔄 进行中 ｜ **负责人**：<agent 名 / 角色>
- **任务类型**：<对应 MAP.md 的 §2.x>
- **最小上下文**：AGENTS.md + <必须读的 1–2 个文件>
- **改了什么**：<文件:符号，逐条>
- **为什么**：<一句话 + 决策编号 D-xxxxxx-xx（若有）>
- **验证状态**：单测 ✅ / 本地 ✅ / 线上 ⬜（未线上验证不标完成）
- **遗留风险**：<已知问题、未覆盖的边界>
- **下一步（给接手者）**：<具体到文件与函数>
```

---

## 3. 上下文预算（防止 agent 全量阅读）

| 阶段 | 允许读取 | 预算 |
|------|----------|------|
| 接单 | `AGENTS.md` + 台账中自己的条目 | ≤ 2 个文件 |
| 开工 | `MAP.md` 对应小节指向的文件 | ≤ 3 个文件 |
| 遇阻 | 追加 `PITFALLS.md` 对应章节 / `DECISIONS.md` 检索 | ≤ 2 个文件 |
| 收尾 | `CONVENTIONS.md` §5 文档同步清单 | 1 个文件 |

**上限原则**：单个 agent 单轮读取**不超过 8 个文件**。超出说明任务该拆分，或路由表需要补充（顺手补 `MAP.md`）。

---

## 4. 并行与冲突仲裁

1. **先登记再动手**：在 `TASK-LEDGER.md` 占条目，写明涉及的文件。
2. **同文件冲突**：后登记者**等待**或改做不重叠的部分；确需同时改，拆成「先改结构 / 后改逻辑」两段接力。
3. **同数据库 migration**：**严格串行**。迁移号按登记顺序分配，禁止跳号；新增迁移必须幂等。
4. **同视觉改动**：串行。视觉基线（`docs/ui-baseline.json`）是全局共享资源，两人同时改会互相污染。
5. **冲突判定不了**：停在台账里写明「冲突点 + 两个方案 + 我倾向哪个」，交给人类裁决，**不要自行 merge**。

---

## 5. 验收清单（接手者核对用）

- [ ] 台账条目四件套齐全
- [ ] 五道门禁全绿：`npm run check` → `lint` → `format:check` → `test -- --run` → `build`
- [ ] 涉及接口 → `docs/API.md` 已同步
- [ ] 涉及功能 → `README.md` / `docs/FEATURES.md` / `docs/USAGE.md` / `CHANGELOG.md` 已同步
- [ ] 涉及 Schema → 新增幂等 migration
- [ ] 涉及视觉 → 已与基线对比（构建期间禁止截图）
- [ ] **线上验证**（`sort.logicc.top`）已完成或明确标注「待线上验证」
- [ ] 若有非显然决策 → 已在 `docs/memory/DECISIONS.md` 顶部新增条目
- [ ] 若踩到新坑 → 已在 `docs/agents/PITFALLS.md` 补充
- [ ] 台账条目状态已更新为 ✅ 或 🔄，并写明交接对象

## 6. 接力模式（三种常用）

### A. 串行接力（一个任务分几段）

```
Agent-1 做结构改动 → 提交 → 写台账 → Agent-2 读台账接手做逻辑 → ...
```
适合：大重构、跨层改动。每段一个 commit，段间可独立回滚。

### B. 并行分工（多个独立子任务）

```
按 MAP.md 的分区切分：前端 agent 改 views / Worker agent 改接口 / 测试 agent 补契约
```
适合：P0/P1 加固那类可分区的工作。必须在台账里标清各自的文件边界。

### C. 评审接力（实现者 → 审查者）

```
实现 agent 标记 🔄 待审 → 审查 agent 按 §5 清单核对 → 通过标 ✅ 或回退写「驳回原因」
```
适合：安全相关改动（SSRF、XSS、鉴权）——**安全改动必须走审查接力**。

---

## 7. 反模式

| ❌ | ✅ |
|----|----|
| 「我已经做完了，你接着优化一下」 | 写明做到哪一步、验证到哪一层、下一步具体做什么 |
| 交接写在对话里 | 写进 `TASK-LEDGER.md` 和 commit message |
| 让接手者自己 `git log` 猜 | 给 commit hash + 一句话 |
| 只说「修好了」不说验证方式 | 区分单测 / 本地 / 线上三层 |
| 遗留风险不写 | 风险必须写，哪怕只是「未覆盖 320px 宽度」 |
