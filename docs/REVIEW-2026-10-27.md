## 二、优化清单

### P0-1 · 撤销走「全量重放」，adaptive 模式实测冻结 13.9 秒

**读码**：`src/lib/ranking.ts:994-1003`（`undoLastAction` 从头 `createRankingState` + 逐步 `replayDecision`）、
`src/lib/ranking.ts:278-296`（`findPath` 每个出队节点都线性扫**全部** `preferenceEdges`）、
`src/lib/ranking.ts:374`（每次 `recordPreference` 都调一次 `findPath`）。
**入口**：`src/views/ProfileView.tsx:806` —— 「返回最后一次取舍」直接戳 `undoLastAction`；
`useSorting.ts:743` 只在快照栈空时才退到这里（`resume()` 在 `useSorting.ts:823` 把快照栈清空了）。

**实测**（临时基准脚本，n 件清单、topN=10，跑完随即删除）：

| 模式 | n | 决策步数 | 单份状态 JSON | 排序总耗时 | **一次撤销** |
|------|---|---------|--------------|-----------|-------------|
| classic | 100 | 333 | — | 23 ms | 18 ms |
| classic | 200 | 663 | — | 68 ms | 68 ms |
| classic | 300 | 1007 | 342 KB | 336 ms | **310 ms** |
| adaptive | 100 | 713 | — | 706 ms | 729 ms |
| adaptive | 300 | 1958 | 661 KB | 14.9 s | **13.9 s** |

主线程同步阻塞：adaptive + 300 件（默认导入上限就是 300）点「返回最后一次取舍」= 冻结约 14 秒，
浏览器大概率弹「页面无响应」。Growth 约 n³，**清单越长越必然触发**。

**建议**（任选，按性价比）：① ProfileView 改用与 `useSorting` 相同的快照栈；
② 快照栈持久化到草稿，撤销不再需要历史；③ `findPath` 改邻接表 + 深度上限（多数情况本就无环）。
**风险**：低。`ranking.test.ts` 已有 golden 覆盖，`replayDecision` 语义不变。

### P0-2 · Jev 代判的 effect 依赖里有每次渲染都变的函数 → 请求结果被丢弃且不重试

**读码**：`src/views/SortingView.tsx:104-115`（deps 含 `t, worksById, act, tasteContext`）、
`:84-88`（`if (assistKeyRef.current === key) return;`）、`:110-113`（cleanup `stale = true`）。
**依赖身份实测**：`App.tsx:122` `const t = (zh, en) => …` 每次渲染新建；
`useSorting.ts:732` `function act(...)` 普通函数、全文件 0 个 `useCallback`。

**影响**：请求飞行期间 App 任意一次重渲染（notice 弹出、草稿落盘、主题切换、进度保存）
→ cleanup 置 `stale = true` → 结果被丢；effect 重跑时 `assistKeyRef.current === key` 命中分支直接 return，
**这一对永不重试**。现象是「AI 代判随机失灵」，且 busy/loading 状态已复位，用户无从判断。

**建议**：deps 收敛为 `[comparison.leftId, comparison.rightId, comparison.phase]`；
`t`/`act`/`worksById` 走 ref 兜最新值，`stale` 只由「键变化」置位。
**风险**：低（只动依赖数组）。验收：开启代判后请求飞行期间手动弹一次 notice，预测仍应落位。

### P1-1 · 每次取舍都 `JSON.stringify` 整个状态并压栈

**读码**：`src/lib/useSorting.ts:748-750`（每步 push 一份 `serializeRankingState`）、
注释自称上限 50 份。**实测**：n=300 时单份 342 KB（adaptive 661 KB）
→ 常驻内存 17 MB（adaptive 33 MB），且每步同步 stringify 数十万字节，直接吃掉点击反馈预算。
**建议**：状态不可变，快照直接浅引用 `push(ranking)`；若必须深拷贝，改存 `decisionLog.length` + 截断。
**风险**：低。

### P1-2 · 广场列表请求无令牌，切筛选会串数据 + 闪假空态

**读码**：`src/views/PlazaView.tsx:56-91`（`loadPosts` 无 AbortController / 无 reqId）、
`:184`（切 tab 时先 `setPosts([])`）、`:283`（空态条件 `!initialLoading && !loading && posts.length === 0`）。
**影响**：`setPosts([])` 到新数据到达之间有一帧满足空态条件 → 每次切 tab 闪一次「广场还没有内容」；
连续切筛选时先发的请求后到会覆盖新结果（tab 显示音乐、列表是电影）。`SourceView.tsx` 的
`setNeteaseConnected/setDbConnected` 同样模式。
**建议**：请求令牌（`const my = ++reqId.current; if (my !== reqId.current) return;`）+ 切筛选不预清空。
**风险**：低。

### P1-3 · 草稿「读侧 1000 硬闸 / 写侧无闸」→ 静默丢全部进度

**读码**：`src/lib/useSorting.ts:61`（`works.length > 1000` 直接 `return null`，继续卡片消失）；
写侧 `loadCustomWorksFn` / `applyImportedWorks` 无上限，`importCap` 允许每次 1000 → 多次导入即可超。
**建议**：读写共用同一个常量（对齐 `profile.ts` 的 `MAX_RANKING_ITEMS`），写侧同样拒绝并提示分榜；
读侧宁可截断 + 提示也不要整体丢。
**风险**：低。

### P1-4 · `useAuth` 仍有部分 fetch 无超时，挂起时按钮永久禁用

**读码**：`src/lib/useAuth.ts` 共 8 处 `await fetch`，其中 6 处已带 `AbortSignal.timeout/controller.signal`
（子 agent 原报「完全没有超时」经核验不成立，已修正）；剩余 `syncProfile` 类路径失败后
`syncing.current` 不复位，`syncStatus` 会永久停在 `saving` 且无重试退避。
**另见 P1-5（更严重）**：`useAuth.ts:357-387` 登出前最后一次云端保存失败被 `catch {}` 吞掉，
随后无条件 `localStorage.removeItem(LIBRARY_KEY)` → 弱网/5xx 时登出即永久丢画像，且无提示。
**建议**：登出前保存失败 → 明确提示并保留 recovery 备份（机制已存在）；同步加失败退避。

### P1-5 · PNG 导出画布无面积上限，失败文案笼统

**读码**：`src/lib/exportPng.ts:168-169`（`MAX_EXPORT_ITEMS=240` / `MAX_EXPORT_POSTERS=80` 只限条数）、
`:262-263`（`canvas.width = W*2; canvas.height = H*2`）、`:239-244`（最多解码 320 张海报常驻 `images` Map）。
**影响**：240 件 single-column 版式 → 画布约 2400×21120（≈50 MPx / 200 MB 后备存储）；
iOS Safari canvas 面积上限低一个数量级（**待真机确认**）→ `toBlob` 返回 null，用户只看到「导出失败，请重试」；
叠加 320 张已解码位图（≈1.5 MB/张）移动端极易 OOM，且画布不做 `width=0` 释放。
**建议**：导出前按面积阈值自动降倍率或分页；只解码最终会被画的那一张；`toBlob` 为 null 走明确降级文案。

### P1-6 · 每张 `<Poster>` 挂载时在 render 阶段同步 parse 整个 sessionStorage 缓存

**读码**：`src/components/Poster.tsx:184-189`（`resolveSync` 在 `useState` 初始化器里 `JSON.parse(sessionStorage)`）、
`:193-201`（写回也是「全量 parse → 删一半 → 全量 stringify」），上限 `POSTER_CACHE_MAX = 500`。
**影响**：一屏上百个 Poster → 同一份 60–100 KB JSON 被重复解析上百次；补图时反复重写整表。
**建议**：模块级惰性单例（只读一次）+ 内存 Map + 防抖 flush。**风险**：低（缓存本就可丢）。
